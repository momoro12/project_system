## Блок 1: Производительность (ПРОИЗ)

| ID | Нефункциональное требование | Уточнения |
|----|-----------------------------|-----------|
| НФТ-ПРОИЗ-01 | Система должна отвечать на стандартные запросы (поиск рейса, просмотр карточки самолёта, проверка статуса билета) не более чем за **2 секунды** | Чтобы кассиры, диспетчеры и сотрудники справочной службы могли работать без задержек |
| НФТ-ПРОИЗ-02 | Формирование сложных аналитических отчётов (например, по отменённым рейсам, продажам билетов, техобслуживанию самолётов) не должно занимать более **5 секунд** | Тяжёлые выборки должны кешироваться или выполняться в фоне |
| НФТ-ПРОИЗ-03 | Система должна поддерживать одновременную работу **до 500 пользователей** без заметной деградации производительности | Пиковые нагрузки: массовая продажа билетов, переносы рейсов, регистрация пассажиров |
| НФТ-ПРОИЗ-04 | Время загрузки рабочих экранов (панель диспетчера, кассовый интерфейс, список рейсов) не должно превышать **2 секунды** | Быстрый доступ к данным в условиях высокой операционной нагрузки |
| НФТ-ПРОИЗ-05 | Операции регистрации пассажиров, оформления багажа и посадки должны выполняться без блокировки интерфейса при обмене с сервером | Чтобы сотрудники стойки регистрации могли обслуживать пассажиров непрерывно |

## Блок 2: Безопасность и защита данных (БЕЗ)

| ID | Нефункциональное требование | Уточнения |
|----|-----------------------------|-----------|
| НФТ-БЕЗ-01 | Все пароли пользователей должны храниться в хешированном виде с использованием современных алгоритмов (bcrypt/Argon2) | Даже при компрометации базы нельзя восстановить пароли сотрудников аэропорта |
| НФТ-БЕЗ-02 | Сессия пользователя должна автоматически завершаться после **15 минут неактивности** | Особенно важно для касс, постов службы безопасности и рабочих мест справочной службы |
| НФТ-БЕЗ-03 | Все соединения с системой должны осуществляться по защищённому протоколу **HTTPS (TLS 1.3)** | Для защиты персональных данных пассажиров и служебной информации о рейсах |
| НФТ-БЕЗ-04 | Система должна блокировать учётную запись после **5 неудачных попыток входа** на 10 минут и уведомлять администратора безопасности | Защита от подбора паролей к учётным записям кассиров, диспетчеров и администрации |
| НФТ-БЕЗ-05 | Конфиденциальные данные работников и пассажиров должны быть защищены в соответствии с требованиями законодательства о персональных данных | Разграничение доступа: кассир видит билетные данные, служба безопасности — документы, кадровая служба — персональные данные сотрудников |

## Блок 3: Интерфейс и удобство использования (ИНТ)

| ID | Нефункциональное требование | Уточнения |
|----|-----------------------------|-----------|
| НФТ-ИНТ-01 | Интерфейс системы должен быть интуитивно понятным: новый сотрудник должен освоить базовые операции за **не более 20 минут** | Продажа билета, поиск рейса, регистрация пассажира и проверка статуса самолёта должны быть очевидны |
| НФТ-ИНТ-02 | Все формы ввода должны иметь валидацию данных с понятными сообщениями об ошибках | Не `"Ошибка"`, а `"Нельзя оформить посадку: для международного рейса отсутствуют данные заграничного паспорта"` |
| НФТ-ИНТ-03 | Система должна корректно отображаться на экранах от **1366×768** и поддерживать адаптивную вёрстку для планшетов | Например, для мобильных рабочих мест сотрудников обслуживания и службы безопасности |
| НФТ-ИНТ-04 | Ключевые действия (поиск рейса, продажа билета, регистрация пассажира, фиксация задержки) должны быть доступны не более чем в **3 клика** от главного экрана | Минимум вложенности в критичных операционных сценариях |
| НФТ-ИНТ-05 | Интерфейс должен обеспечивать повышенную читаемость данных на экранах в условиях круглосуточной работы | Контрастные элементы, чёткая типографика и удобство работы в ночные смены |

## Блок 4: Надёжность и доступность (НАД)

| ID | Нефункциональное требование | Уточнения |
|----|-----------------------------|-----------|
| НФТ-НАД-01 | Система должна быть доступна **не менее 99.9% времени** в периоды штатной эксплуатации | Простой системы напрямую влияет на рейсы, продажи билетов и обслуживание пассажиров |
| НФТ-НАД-02 | При сбое соединения несохранённые данные в формах регистрации, продажи билетов и оформления багажа должны автоматически сохраняться локально | Чтобы сотруднику не приходилось повторно вводить данные пассажира |
| НФТ-НАД-03 | Система должна корректно восстанавливаться после кратковременных сетевых сбоев без потери подтверждённых операций | Особенно важно для кассовых и регистрационных операций |
| НФТ-НАД-04 | Ошибки в одном модуле не должны приводить к отказу всей системы | Если модуль аналитики недоступен, регистрация пассажиров и управление рейсами должны продолжать работу |
| НФТ-НАД-05 | Система должна автоматически уведомлять пользователей о плановых технических работах не менее чем за **24 часа** | Чтобы подразделения аэропорта могли заранее скорректировать свою работу |

## Блок 5: Сопровождаемость и развитие (СОПР)

| ID | Нефункциональное требование | Уточнения |
|----|-----------------------------|-----------|
| НФТ-СОПР-01 | Код системы и API должны быть документированы | Документация должна позволять новым разработчикам быстро разобраться в архитектуре и точках интеграции |
| НФТ-СОПР-02 | Система должна иметь модульную архитектуру, позволяющую добавлять новые категории рейсов, типы самолётов и сценарии обслуживания без переписывания ядра | Например, добавление нового типа специального рейса должно требовать минимальных изменений |
| НФТ-СОПР-03 | Все изменения структуры базы данных должны сопровождаться версионными миграциями | Чтобы сохранялись исторические данные по рейсам, билетам, осмотрам и кадровому составу |
| НФТ-СОПР-04 | Система должна предоставлять API для интеграции с внешними сервисами и внутренними подсистемами аэропорта | Погодные сервисы, бухгалтерские системы, табло вылетов, внешние билетные сервисы |
| НФТ-СОПР-05 | Журналирование должно быть структурированным и поддерживать уровни логирования (INFO, WARN, ERROR) | Для быстрого поиска причин инцидентов и анализа работы системы |

## Блок 6: Портативность и развёртывание (ПОРТ)

| ID | Нефункциональное требование | Уточнения |
|----|-----------------------------|-----------|
| НФТ-ПОРТ-01 | Система должна развёртываться на ОС семейства **Linux (Ubuntu/AlmaLinux)** | Соответствие типовой серверной инфраструктуре предприятия |
| НФТ-ПОРТ-02 | Развёртывание должно осуществляться в контейнеризированной среде с использованием **Docker Compose** или Kubernetes | Упрощение установки, масштабирования и сопровождения |
| НФТ-ПОРТ-03 | Система должна корректно работать с СУБД **PostgreSQL 14+** | Для надёжного хранения операционных, кадровых и билетных данных |
| НФТ-ПОРТ-04 | Веб-интерфейс должен работать в современных браузерах (Chrome, Firefox, Edge, Safari) последних 2 версий | Без необходимости установки специализированного ПО на клиентские машины |
| НФТ-ПОРТ-05 | Клиентская часть должна поддерживать развёртывание в локальной сети аэропорта и, при необходимости, доступ через защищённый внешний контур | Для разделения внутреннего и внешнего доступа к функциональности системы |

## Блок 7: Целостность и резервирование данных (ДАН)

| ID | Нефункциональное требование | Уточнения |
|----|-----------------------------|-----------|
| НФТ-ДАН-01 | Система должна выполнять автоматическое резервное копирование базы данных **ежедневно**, а критических операционных данных — с повышенной частотой | Чтобы обеспечить восстановление после сбоев без существенной потери информации |
| НФТ-ДАН-02 | Резервные копии должны храниться **не менее 90 дней** с возможностью точечного восстановления данных | Например, для восстановления информации о возвратах билетов или изменениях расписания |
| НФТ-ДАН-03 | Все операции изменения критических данных должны выполняться в **ACID-транзакциях** | Продажа билета, возврат, регистрация пассажира, назначение самолёта и фиксация техосмотра должны быть атомарными |
| НФТ-ДАН-04 | Система должна контролировать целостность связей и запрещать удаление объектов с активными зависимостями | Нельзя удалить рейс, если по нему проданы билеты, или самолёт, если он участвует в расписании |
| НФТ-ДАН-05 | Подтверждённые операционные записи должны сохранять историю изменений и не допускать несанкционированного редактирования задним числом | Особенно для данных о рейсах, посадке, возвратах билетов, медосмотрах пилотов и техосмотрах самолётов |
